# План реалізації Sculk

*[English](PLAN.md) · Українська*

Робочий список задач за концепцією з [docs/uk/](docs/uk/README.md). Позначка `[x]` — зроблено й перевірено, `[~]` — у роботі або зроблено частково (деталі в примітці), `[ ]` — ще не почато. Блоки йдуть у порядку, в якому їх варто робити.

Як перевіряти: `cargo test --workspace`, `cargo clippy --workspace --all-targets`, і наскрізний запуск `cargo run -- dev` з клієнтом Minecraft 26.3 або ботами Horizon:

```sh
cargo run -- prepare                        # один раз: дані 26.3 з server.jar у game-data/
cargo run -- dev --workers 2
(cd external/horizon && cargo build --release -p horizon-bots)
external/horizon/target/release/horizon-bots --server 127.0.0.1:25565 --bots 5 --behaviour mixed --report -
```

Ванільна гра (рушій Horizon) замість плаского світу: ті самі ролі, плюс рушій і підготовлені ресурси Horizon
(`horizon-prepare --prepare --server-jar ...`, або тека `.local/horizon-client/26.3` лаунчера Horizon):

```sh
cargo build --profile fast -p sculk -p sculk-engine
SCULK_ENGINE=target/fast/sculk-engine SCULK_RESOURCES=<ресурси>/26.3 SCULK_EULA=true \
  SCULK_PROPERTIES=config/server.properties target/fast/sculk dev --workers 2
# консоль: op <гравець>, whitelist ..., say ..., stop (зберігає світ і гравців)
# боти літають: для них gamemode=creative, allow-flight=true у server.properties кластера
```

У Docker: `tools/docker.sh up` (у `.env`: `HORIZON_RESOURCES`, `SCULK_EULA=true`; `config/` — спільні
`server.properties` і `server-icon.png`).

## Основа — Horizon

Sculk будується на коді [Horizon](https://github.com/horizon-rust/horizon) (MIT), а не переписує ваніль сам: так легше переходити на нові версії гри разом із Horizon.

- `external/horizon` — upstream на коміті з `patches/horizon/BASE` плюс наші патчі з `patches/horizon/*.patch`, гілка `sculk`. Відтворити: `tools/horizon.sh setup`.
- Чого бракує в Horizon — дописуємо патчем у сам Horizon (коміт на гілці `sculk`, потім `tools/horizon.sh export`), а не копіюємо код у Sculk.
- Оновлення Horizon: rebase гілки `sculk` на новий upstream, новий `BASE`, `tools/horizon.sh export`.

Що вже береться з Horizon: увесь рушій гри (`sculk-engine`), `horizon-protocol` (пакети 26.3, кадрування, стиснення, Velocity forwarding), `horizon-world` (NBT, region-файли), `horizon-bots` (тестовий клієнт). Патчі: `patches/horizon/0001`–`0007` (блок B). Увага: `external/rustfmt.toml` не дає `rustfmt.toml` Sculk переформатувати Horizon.

## B. Ванільна логіка в MW (Horizon)

Що з'ясовано (10.11.2026):
- Сервер Horizon — це `Game<'_>` з `horizon-client` (`game/dedicated.rs`, `lan/hub.rs`): той самий об'єкт, що й клієнт із рендером, плюс кілька глобальних `static` (`dedicated::SETUP`, `lan/handoff`). Тисячі таких на процес — не варіант.
- Horizon сам планує `tick = "regions"` (docs/server-next.md §4.2): групи чанків далі 2 чанків одна від одної, кожна зі своїм random, діапазоном entity ID і чергою запланованих тіків, які зливаються й діляться з рухом гравців. Це MW Sculk в одному процесі. У коді цього ще немає.
- Винести серверну половину `Game` у бібліотеку Horizon теж планує (docs/layers.md, крок P), але не поспішає.

Обраний шлях (10.11.2026): **воркер = рушій Horizon** (`sculk-engine`: dedicated-сервер Horizon, до якого Sculk додає свої хуки, як `horizon-official` додає свої). Увесь ванільний геймплей — від Horizon; Sculk дає світ в AnvilDB під орендами, маршрутизацію гравців і кластер. Регіони Horizon (`tick = "regions"`) потім стануть MW усередині рушія.

Підпис SigV4 перевірено на еталонному прикладі AWS (і HMAC — на RFC 4231), архівування й повернення — через фальшивий бакет; справжнього AWS тут немає

## D. Життєвий цикл MW

- [x] Ріст зони з рухом гравців: дозамовлення нових чанків і звільнення непотрібних (зона = об'єднання квадратів навколо гравців MW)

MW у режимі рушія = рушій воркера: свої тіки, свої оренди. IO розводить гравців по рушіях (`SCULK_PLACEMENT=spread`, за замовчуванням; `single` — усі в одному) і зводить їх докупи, коли їхні зони зустрічаються.

- [x] Народження за зоною появи: IO читає збережену позицію гравця (`players/data/<uuid>.dat` з AnvilDB) і веде його до рушія, що володіє тим чанком; немає власника — до рушія з найменшою кількістю гравців (рахуються й ті, хто саме заходить)
- [x] Злиття між воркерами (24.11.2026): рушій, якому відмовили в оренді, повідомляє IO (`ReportConflict`); якщо в рушія-власника біля чанка є гравці, гравці одного рушія поблизу переносяться на інший без розриву з'єднання (див. блок B). Перевірено наживо: 6 ботів на 3 рушіях біля спавну → один рушій; A на 3000/3000 на рушії 2, B біля спавну на рушії 1 → `tp B0` до A → A переноситься на рушій 1; 0 помилок, 0 падінь
- [x] Якщо біля чанка гравців власника немає (вони пішли, рушій ось-ось відпустить чанк), рушій чекає на чанк до 20 с замість згенерувати чужу копію
- [x] Перенесення одного гравця між MW при телепорті/порталі/респавні: телепорт у зону іншого рушія — це той самий конфлікт оренди → злиття (перевірено з `/tp`)
- [x] Розщеплення: IO раз на 5 с групує гравців рушія за відстанню; коли зони груп ≥ 8 чанків одна від одної 5 хвилин (`SCULK_SPLIT_GAP`, `SCULK_SPLIT_AFTER_SECS`), група без засновника (найстаріша сесія) переїжджає на вільний рушій. Перевірено наживо (поріг 10 с): A0 пішов на 3000 → переїхав на рушій 2, який дочекався справжніх чанків
- [x] Одночасне злиття: поглинає рушій із більшою кількістю гравців, при рівності — з меншим ID воркера; одне злиття пари рушіїв за раз; гравець після перенесення 15 с не переїжджає знову (без пінг-понгу)
- [x] Злиття на одному воркері: той самий hand-over (через localhost), якщо на воркері кілька рушіїв
- [x] Міграція для балансу: рушій, що не встигає (`SCULK_SPLIT_OVERLOAD_MSPT`, 45 мс на тік), розводить свої мікросвіти по вільних рушіях одразу, не чекаючи 5 хвилин; воркер, що зупиняється, віддає всіх гравців іншим рушіям (блок F)

## E. Планувальник воркера

- [~] Пул потоків: кожен MW — окремий процес-рушій зі своїм тіком і пулом потоків Horizon за кількістю ядер; MW на різних рушіях тікаються паралельно, розподіл ядер між ними робить ОС. Кількох MW усередині одного процесу (і розкладача по потоках) немає — це `tick = "regions"` Horizon (блок B)

## F. Надійність

- [x] Відновлення після смерті воркера: IO звільняє оренди, гравці при перезаході йдуть на резервний воркер, той піднімає рушій зі світом і гравцями з AnvilDB (перевірено: SIGKILL основного воркера, 2207 оренд звільнено, 3 боти зайшли на резервний, 0 помилок). Втрачається прогрес з останнього автозбереження
- [x] Гравця переносять без розриву: поки клієнт не підтвердив повернення в конфігурацію, його keep-alive іде старому рушію; далі keep-alive веде новий рушій (переключення займає ~0,3 с, тож IO не мусить відповідати сам)
- [x] Смерть воркера без відключення гравців: коли з'єднання з рушієм рветься, а воркера в IO вже немає (не кік), IO переводить гравця на інший рушій, той вантажить його з AnvilDB. `tools/chaos.sh`: 3 вбивства найзавантаженішого воркера під 12 ботами — 36 порятунків, 0 відключених, 0 падінь рушіїв, 0 відхилених записів

Перевірено: 4 боти переїхали, 0 помилок. Якщо інших рушіїв немає — гравці зберігаються, як на ванільному stop
- [x] Режим «AnvilDB недоступна»: записи чанків стають у чергу (новіший запис чанка заміняє старіший, читання бачить чергу), чанки з невідісланими записами не віддають оренд; читання й нові оренди чекають до 30 с; IO не пускає нових гравців. Перевірено: AnvilDB вимкнена 15 с під ботами — 0 помилок, 0 падінь, черга дописалась

## I. Перевірка масштабу

- [~] Навантаження ботами: 40 ботів на одному рушії — MSPT 12–14 мс (бюджет 50), 45 тис. чанків, 0 помилок.
